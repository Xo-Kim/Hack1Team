# 연출 설계 — 조명 · 음향 · 공유

고객이 실제로 만나는 것은 이 문서에 적힌 것뿐이다. 분석 결과도, 추천도 화면에 나오지
않으므로 **조명·음악·컨셉명이 AI 가 한 일의 유일한 표현**이다.

---

## 1. 조명 연출

### 1.1 웹에서의 조명 렌더링

"화면 배경색이 바뀐다" 수준으로는 조명으로 인지되지 않는다. 세 가지를 중첩한다.

1. **카메라 영상 자체에 조명 적용 (핵심)** — `<video>` 에 CSS `filter: hue-rotate() saturate() brightness() contrast()` + 컬러 오버레이 `mix-blend-mode: overlay | soft-light`. 화면 속 **자기 얼굴과 옷의 색이 실제로 변한다.** 조명 인지가 배경이 아니라 자기 자신에서 발생한다.
2. **레이어드 광원 연출** — 풀스크린 radial/conic 그라디언트 2~3장, 비네팅, 필름 그레인 오버레이, 미세 breathing 애니메이션(밝기 ±3%, 6초 주기).
3. **느린 전환** — 2.5~3초 `ease-in-out`. 즉시 전환은 "색 바뀜", 점진 전환은 "조명이 들어옴"으로 읽힌다.

밝은 씬에서는 틴트 투명도를 자동으로 낮춘다. 안 그러면 화면이 하얗게 날아간다.

### 1.2 디스플레이는 실제 광원이다

어두운 환경에서 대형 디스플레이 전면이 특정 색으로 물들면, 앞에 선 사람에게 **실제로
그 색의 빛이 떨어진다.** 시뮬레이션이 아니다. 실제 스마트 미러도 하프미러 글래스 뒤에
디스플레이를 두는 구조이므로, 이는 프로토타입 편법이 아니라 **실제 제품과 동일한
구현 방식**이다.

> 데모 환경 요구사항: 부스 조명이 밝으면 효과가 죽는다. **저조도 위치 확보를 사전 협의**할 것.

### 1.3 하드웨어 중립 설계

`lighting` 객체는 특정 하드웨어에 종속되지 않는 추상 스펙으로 정의하고, 렌더러를
교체 가능한 구현체로 둔다.

```
LightingSpec (색상 / 색온도K / 밝기 / 전환ms / 이펙트)
        │
        ├─ WebRenderer      → CSS·Canvas          (구현됨)
        ├─ HueAdapter       → Philips Hue REST     (미구현·컨셉)
        └─ DMXAdapter       → DMX512 / Art-Net     (미구현·컨셉)
```

**이 스펙에 CSS 전용 속성을 추가하지 말 것.** 추가하는 순간 하드웨어 중립이 깨진다.

발표 논지: **"우리는 이미 조명 제어 신호를 생성하고 있다. 웹은 그 신호의 렌더러 중
하나일 뿐이며, 실제 조명 연동은 어댑터 추가로 가능하다."**

실제 매장 적용 시의 현실적 제약:

- 매장 전체 조명은 제어 대상이 아니다. **미러 존 전용 조명기구 1~3개**의 존 단위 제어.
- 음향도 매장 BGM 교체가 아닌 **지향성 스피커** 기반 존 단위 재생.
- 상업 공간 조명 제어 프로토콜: DMX512/Art-Net(연출조명), Philips Hue·Casambi(BLE)·DALI(건축조명).

## 2. 음향

### 2.1 브랜드 정합성

**MCM 의 음악적 뿌리는 80~90년대 힙합·스트릿이다** (PRD §3.2). 음향이 앰비언트·명상
계열로 흐르면 스파나 갤러리의 소리가 되어, 바텀업 전략과 정면으로 충돌한다.

두 곳에서 이를 강제한다.

1. **선곡** — `genre_hint` 를 hiphop/rnb/soul/funk/electronic 계열 `enum` 으로 제한.
   ambient·lounge 는 아주 미니멀한 착장에만 예외 허용.
2. **폴백 앰비언스** — 음원 재생이 막혔을 때 도는 절차적 사운드에도 킥·스네어·하이햇·
   서브베이스를 얹는다. 드론만 깔면 방향이 반대로 간다.

> 초기 구현은 이 지점을 놓쳤다. 안정성(자산·라이선스·네트워크 불필요)만 보고
> 앰비언트 드론을 골랐고, **기술적 제약이 브랜드 결정으로 새어 나갔다.**
> 음향 소스를 바꿀 때마다 이 절을 먼저 확인할 것.

### 2.2 재생 경로

```
분석 결과의 MusicSpec
   ├─ energy       → Jamendo speed (verylow ~ veryhigh)
   └─ queryTags + genreHint → fuzzytags
              ↓
      Jamendo 후보 10곡
              ↓
      GPT 가 그중 1곡 선택 + 이유  ← 제품 추천과 같은 패턴
              ↓
      서버가 후보 목록과 대조 → <audio> 재생 (loop)
      실패하면 검색 1위, 후보가 없으면 절차적 앰비언스
```

**소리가 아예 안 나는 상태는 만들지 않는다.**

검색은 `order` 가 아니라 `boost` 를 쓴다. 공식 문서 경고대로 `fuzzytags` 검색에
`order` 를 지정하면 **검색 관련성 순서가 통째로 사라지고 인기순으로만 정렬되어**
무드 매칭이 무의미해진다.

태그를 좁게 걸면 0건이 되기 쉬워 **단계적으로 넓혀가며 재시도**한다
(전체 태그 + 에너지 → 전체 태그 → 장르만 → 최후 폴백). 2회차부터는 `speed` 조건도
푼다 — 태그만 넓히고 에너지를 고정하면 계속 0건이 나온다.

LLM 이 뱉는 `"dark r&b"` 같은 구는 URL 을 깨뜨리므로 알파벳/숫자만 남겨 단어로 쪼개고
2글자 이하는 버린다.

### 2.3 절차적 앰비언스

`key`/`scale`/`bpm`/`energy` 를 실제로 소비한다 — 근음+5도 드론, 느린 필터 LFO,
펜타토닉 아르페지오, 생성된 IR 리버브, 그리고 **킥·스네어·하이햇·서브베이스 비트**.

드럼은 `setInterval` 로 직접 치지 않는다. 타이밍이 흔들려 바로 티가 나기 때문에,
짧은 주기로 깨어나 `ctx.currentTime` 기준으로 앞당겨 예약하는 **lookahead 스케줄링**을 쓴다.

### 2.4 라이선스

**재생 중인 곡의 아티스트명과 출처 링크는 화면에서 지우지 말 것.**
Jamendo 의 CC 라이선스는 대부분 저작자 표시(BY)를 요구한다. 장식이 아니라 준수 요건이다.

> **⚠ 실제 매장 도입 시 확인 필요**
> Jamendo 응답의 `licenses.ccnc` 를 읽어 `commercialOk` 로 내려보낸다.
> **문제는 실측 결과 후보 10곡이 전부 비상업(NC) 조건이었다는 것이다.**
> 해커톤 시연은 무관하지만 매장 영업은 상업적 이용이므로 그대로는 못 쓴다.
> 실서비스 전에 `probackground=true`(매장 배경음악 상업 프로그램 등록 곡만)로
> 좁히거나, 브랜드 큐레이션 플레이리스트로 전환해야 한다.
> 지금은 후보를 거르지 않는다 — 거르면 후보가 0곡이 되기 때문이다.

### 2.5 정지 조건

소리에는 **끝나는 조건이 반드시 있어야 한다.** 음소거 버튼과 무입력 타임아웃
두 가지를 둔다. 루프 재생만 걸어두면 고객이 떠난 뒤에도 매장에서 계속 울린다.

## 3. 공유 — 서비스는 사진을 만들지 않는다

### 3.1 결정

**서비스는 사진을 촬영·생성·전송·저장하지 않는다.** 고객이 원하면 자기 휴대전화로
직접 찍는다.

이유는 하나다. **사진을 만들면 사진을 보관해야 한다.** QR 로 전달하려면 고객 폰이
접근할 URL 이 있어야 하고, URL 이 있으려면 바이트가 서버 어딘가에 있어야 한다. 그러면
저장소·토큰·TTL·삭제 배치가 따라오고, [PRIVACY](PRIVACY.md) 의 "아무것도 남기지 않는다"가
*"분석 이미지는 안 남기지만 촬영 사진은 잠깐 남깁니다"* 라는 조건부 약속으로 내려앉는다.

**조건이 붙은 프라이버시 약속은 발표에서 방어하기 어렵고, 무엇보다 사실이 아니게 된다.**

### 3.2 대신 하는 일 — 찍고 싶은 화면을 만든다

공유가 바텀업 전략(PRD §3)의 작동 부품이라는 판단은 그대로다. 바뀐 것은
**누가 결과물을 만드는가**다.

| | 서비스가 만들 때 | 고객이 만들 때 |
|---|---|---|
| 결과물 소유 | 서비스 → 고객에게 전달 | **처음부터 고객 것** |
| 통제 수단 | 프레임·워터마크·다운로드 페이지 | **조명·구도·컨셉명 타이포그래피** |
| 프라이버시 부담 | 저장·TTL·토큰 URL | **없음** |
| 실패 지점 | 업로드·QR 발급·다운로드 | **없음** |
| 확산 측정 | 다운로드 수 | 직접 측정 불가 |

**인생네컷·포토이즘 등 셀프 포토부스가 Gen Z 의 공유 의례로 정착해 있다**는 판단은
유효하다. 다만 우리는 그 의례를 대행하지 않고, **그 의례가 일어날 만한 장면을 제공**한다.
포토부스가 프레임을 바꾸는 데 반해 **우리는 빛을 바꾸므로**, 고객이 자기 폰으로 찍어도
AI 연출은 그대로 사진에 담긴다. 프레임과 달리 빛은 카메라를 가리지 않는다.

### 3.3 설계 원칙

- **촬영을 권유하지 않는다.** 버튼·카운트다운·"찍으시겠어요?" 문구 모두 두지 않는다.
  권유하는 순간 서비스가 결과물의 공동 생산자가 되고, 고객은 브랜드가 시킨 일을 하게 된다.
- **연출을 오래 유지한다.** 응대가 끝난 뒤에도 조명·음악·컨셉명이 유지된다.
  찍을지 말지는 고객이 정하되, **찍을 시간은 확보해 준다.**
- **컨셉명은 화면에 크게, 로고는 얕게.** 사진에 담기는 브랜드 흔적은 컨셉명
  타이포그래피다. 로고를 크게 박으면 광고가 되고, 광고는 공유되지 않는다.
- **화면에 제품명·가격·구매 유도 문구를 두지 않는다.** AI 출력 비공개 원칙이 곧
  "찍을 만한 화면"의 조건이기도 하다. 가격표가 찍힌 사진은 아무도 올리지 않는다.

### 3.4 이 결정의 비용

정직하게 적어 둔다. **잃은 것이 있다.**

| 잃은 것 | 영향 |
|---|---|
| 브랜드 프레임을 결과물에 강제하는 수단 | 공유된 사진에 MCM 표식이 없을 수 있다 |
| 확산의 정량 측정 | KPI 를 대리 지표로 교체 (PRD §5.2) |
| 다운로드 페이지를 통한 재방문 고리 | 재방문 유도 수단 하나가 사라짐 |
| 심사위원에게 사진을 쥐여주는 시연 임팩트 | 데모 성공 기준에서 제외 |

이를 감수하는 근거는 PRD §2.4 다. **욕망의 현관이 상류로 이동하면서 신뢰가 장인정신만큼
중요해지는** 국면이고, "우리는 당신의 사진을 갖지 않습니다"는 그 자체로 전달할 가치가
있는 브랜드 메시지다. 프레임 하나를 강제하는 것보다 크다고 판단했다.

> **연출의 책임이 커졌다.** 서비스가 사진을 만들어주지 않으므로, 고객이 폰을 꺼내게
> 만드는 것은 전적으로 화면 연출의 몫이다. 조명과 컨셉명 타이포그래피가 "찍을 만한
> 화면"인지가 확산 경로 전체의 성패를 결정한다.

> **대체 아이디어 (미결)**: 브랜드 표식을 남기고 싶다면 **화면 자체에 컨셉명과 함께
> 매장 위치·날짜를 조형적으로 배치**해 두는 방법이 있다. 고객이 화면을 찍으면 자연히
> 담긴다. 강제는 아니지만 비용도 없다.
